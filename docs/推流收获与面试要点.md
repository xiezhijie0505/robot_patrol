# 推流收获与面试要点

> 对应已打通的能力：板端摄像头 → H.264 硬编 → MediaMTX → RTSP → Windows VLC  
> 重点收获按三条记：**远程看画面的便捷**、**GStreamer/RTSP 等概念入门**、**联调时重视日志输出**。

---

## 1. 这次收获（三条）

1. **体会到把板上画面放到 Windows 上播放的便捷**  
   不必先做板端 Qt 界面，VLC 打开一个地址即可远程预览，适合巡逻/监控演示。

2. **对 GStreamer、RTSP（以及 H.264）有了能讲清楚的了解**  
   知道管道怎么串、RTSP 地址是什么、编码和拉流协议不是一回事。

3. **联调排障时体会到输出/日志很重要**  
   靠状态和驱动日志定位问题（如 WiFi 握手成功后被踢、自启抢网卡、摄像头被占），以后写程序或调试会有意识先看输出再改。

---

## 2. 必须能说清的流程

```text
摄像头采集 → GStreamer 硬编 H.264 →（本机 UDP / MPEG-TS）→ MediaMTX → RTSP → Windows VLC 播放
```

补充两句：

- **为啥要推流：** 板子画面方便在电脑上远程看。  
- **为啥分两段：** GStreamer 负责采和编；MediaMTX 负责对外提供 RTSP（板上缺现成 RTSP 服务端）。

### 实现过程（叙事版）

1. 确认摄像头能采集（如 `/dev/video9`，必要时停 DMS）。  
2. 目标：Windows 上能看 → 选用 H.264 压缩 + RTSP 访问。  
3. 查板上能力：有硬编（`mpph264enc`），无方便的 RTSP 服务端；无 ffmpeg，有 GStreamer。  
4. 下载部署 MediaMTX（arm64），配置路径 `cam`，从本机 UDP 5004 收流。  
5. 后台起 MediaMTX，前台跑 GStreamer 推流；VLC 打开 `rtsp://板子IP:8554/cam` → 成功。

---

## 3. 必须能各用一句话说清的概念

| 概念 | 一句话 |
|------|--------|
| **GStreamer** | 音视频管道工具；用「元件 ! 元件」把采集、编码、发送串起来。 |
| **H.264** | 视频压缩格式；把画面压小再传。 |
| **硬编码 / mpph264enc** | 用芯片压 H.264，省 CPU；是板上 GStreamer 插件，不是手写编码算法。 |
| **RTSP** | 拉流用的协议；给 `rtsp://IP:端口/路径` 让播放器来看。 |
| **MediaMTX** | 现成的流媒体服务，在板子上开 RTSP。 |
| **路径名 cam** | 配置里给流起的名字，与 VLC 地址里的 `/cam` 对应（可改名，两边一致即可）。 |
| **UDP 5004 / MPEG-TS** | GStreamer 与 MediaMTX 在本机交接码流的方式；端口双方写死一致即可。 |

可选加一句：

- **FFmpeg vs GStreamer：** 都能做音视频处理；板上有 GStreamer 和硬编、没有 ffmpeg，所以用 GStreamer。

---

## 4. 排障例子（对应收获第 3 条，备 1～2 个）

讲清「现象 → 怎么想 → 结论」即可，不必背命令：

- WiFi：日志里认证/关联/四次握手成功后出现对端断开 → 对上曾在手机热点里移除设备连接。  
- 环境：开机 WiFi 自启/重连或 DMS 占摄像头 → 先消除冲突再推流。  
- 感悟：先看输出和日志，再改配置，不凭感觉反复试。
